# 무료 요금제에서 5분 수집 가능성 확인

공식 문서 확인일: 2026-10-23. Edge Function 배포와 서버 일회 수집·DB 저장은 성공했다. 사용자 A1·B1 승인 후 5분 수집·매시간 만료 정리 Cron도 활성화했다. 첫 예약 실행의 HTTP 200·정상 상태 3개 저장을 확인했다. 서버 수집 인수인계에 결과를 기록했다.

## 선택과 결론

- 사용자는 Supabase 실행 1안을 선택하면서 무료 요금제 가능 여부를 질문했고, 수집 주기는 5분(1안)을 선택했다.
- 현재 공식 제공 기능·호출 한도 기준으로 이번 소규모 수집을 무료 범위에서 시작할 수 있다.
- 가격·한도 확인은 실행 성공 증거가 아니다. Supabase 실행 환경에서 서울시 요청·DB 저장을 한 번 검증했다. 예약 호출과 다음 주기의 저장 성공은 별도로 확인해야 한다.

## 기능과 예상 사용량

| 항목 | 현재 무료 범위 또는 제한 | 우리 계획·확인 방법 |
| --- | --- | --- |
| Edge Function 호출 | 월 500,000회 | 1회 실행에 전체 대상 배치 처리 시 5분 간격은 30일 8,640회, 31일 8,928회. 각각 약 1.73%, 1.79% |
| DB 크기 | 프로젝트당 500MB | 실제 테이블·인덱스·오류 원본·작업 이력을 측정. 행 수만으로 용량 확정하지 않음 |
| 외부 전송량 | 5GB | 함수 응답은 최소 집계만 반환하고 실제 사용량 확인. 서울시에서 받아온 바이트를 그대로 Supabase의 청구 전송량으로 계산하지 않음 |
| 함수 실행 시간 | 무료 worker 최대 150초, 요청당 CPU 2초 | 직접 JSON 조회로 시작. 지역 요청 병렬 처리와 접근 실패 1회 재시도를 포함한 최악 실행 시간도 확인 |
| Cron | pg_cron과 pg_net으로 함수 호출 가능 | 5분마다 수집 함수 1회, 시간당 정리는 SQL 작업으로 구분 |

월 호출 계산: `24 × 60 ÷ 5 × 월 일수`. 시설 15개를 함수 15개로 각각 호출하는 것이 아니라 함수 1회가 지역 응답을 받아 시설별 결과를 저장하는 계획이다.
시험 실행·수동 호출·별도 함수·조직의 다른 프로젝트 사용량은 이 계산에 포함되지 않는다. 호출량은 조직 합산 한도도 함께 확인한다.

15곳을 매번 성공 수집해 새 이력을 만들 경우, `15 × 288회/일 × 7일 = 30,240행`의 상태 이력과 기본 수집 기록이 각각 생긴다.
재시도가 있으면 수집 기록은 더 늘어난다. 7일 초과 데이터와 해당 작업 로그를 정리하고 실제 DB 크기를 측정해야 한다.
시간당 정리 지연, 인덱스 공간, PostgreSQL의 삭제 후 공간 재사용도 고려한다. 7일 보관이 DB 파일 크기를 즉시 줄인다는 뜻은 아니다.

## 제한과 다음 검증

- 무료 프로젝트는 7일간 사용량이 낮으면 일시 정지될 수 있다. 무료 운영에 무중단 SLA가 있는 것으로 설명하지 않는다.
- PC에서 서울시 JSON을 읽은 결과와 Supabase 서버에서 읽는 결과는 다를 수 있다. 배포한 환경의 첫 요청·시간·저장은 확인했다(4곳 중 정상 3개, 원천 상태 이상 1개). 반복 운영 성공까지 의미하지 않는다.
- 무료 worker 시간 제한 때문에 수집기를 무한 반복하지 않는다. Cron이 짧은 일회 함수를 5분마다 호출한다.
- 플랫폼의 API·DB 로그 보관과 우리가 직접 만든 `parking_collection_attempts`의 7일 보관 정책은 다른 항목이다.
- 5분은 우리 수집 간격이며 제공처 현황이 5분마다 갱신된다는 보장은 아니다.
- 이 단계에서 유료 요금제로 바꾸거나 유료 부가 기능을 만들지 않았다.

## 화면 조회의 추가 사용량

`parking-status` 조회도 Edge 호출에 합산된다. 실데이터 페이지 첫 로드·수동 새로고침·실데이터 모드 재진입마다 호출하며, 원격 수집 예약 8,640회 계산에 이 화면 조회는 포함되지 않는다. 화면의 30초 최신성 재판정은 네트워크 호출을 하지 않는다. 실제 사용량을 함께 확인한다.
