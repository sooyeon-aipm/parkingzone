## 실제 완료한 것

1. [수집 함수](functions/collect-seoul-parking/index.ts)를 `collect-seoul-parking` 이름으로 Supabase에 배포했다.
2. [서버 전용 RPC](migrations/202610230001_collection_rpc.sql)를 실제 DB에 만들었다. 시작·중복 방지·완료 저장·재시도·만료 정리 기능이다.
3. 인증 없는 서버 호출은 HTTP 401로 거절됐다. 서버 인증 테스트는 현재 default secret 키의 `apikey` 헤더로 성공했다. JWT 검증 스위치는 켠 상태를 유지했다.
4. 첫 성공 응답은 HTTP 200, 대상 4개, 종료 4개, 새 상태 이력 3개, 원천 상태 이상 1개, 재시도 0개였다.
5. 당시 서버 응답의 `completed_at`은 `2026-10-22T15:22:25.989Z`였다(한국 시간 2026-10-23 00:22:25.989). 관찰 당시 값이며 현재 주차 현황이 아니다.
6. 별도 SQL 재조회로 3곳의 새 정상 상태와 강변의 SOURCE_STATUS_2를 확인했다. 강변의 이전 정상 기록은 덮어쓰지 않았다.
7. 로컬 Deno 검사 10개와 새 RPC의 실DB 검사 7개가 통과했다. 실DB 검사 입력은 되돌려 남기지 않았다. 앞선 기본 테이블 제약 검사 10개와 구분한다.

실제 배포한 함수: https://supabase.com/dashboard/project/ksuzhoeahgqbvrbchwpb/functions/collect-seoul-parking/details

현재 수집 대상은 DB에 등록된 강변·성수2가1동·서울숲아이티밸리·갤러리아포레 더몰 상가 4곳이다.

## 코드의 흐름

`시도 시작 → 같은 지역끼리 요청 → 원천 ID·주소·연계 상태·면수·시각 검사 → 상태 저장과 시도 종료를 함께 처리`.

- 두 지역 요청은 병렬 처리한다. 한 요청은 20초 제한, 접근 실패만 30초 후 1회 재시도한다.
- 원천 상태 0/2/3/미정 코드는 `SOURCE_UNAVAILABLE`이며 정상 상태 이력을 추가하지 않는다.
- 성공 원본은 따로 보관하지 않는다. 오류는 확인에 필요한 최소 필드만 4KiB 이내로 남긴다.
- 오래된 원천 시각을 가진 정상 수치도 이력에는 남길 수 있다. 화면용 조회에서 20분 지연을 별도 판단한다.
- 원천 시각이 없으면 NULL과 `SOURCE_TIME_MISSING`으로 저장한다.
- 중복 실행은 DB 잠금과 진행 중 시도 확인으로 막는다. 3분 넘게 종료되지 않은 시도는 다음 실행에서 `WORKER_INTERRUPTED`로 종료한다. 이 3분은 150초 무료 실행 제한보다 여유 있게 둔 복구 기준이며 제공처 최신성 기준이 아니다.
- 완료 요청을 다시 보내도 같은 시도의 상태가 중복 저장되지 않는다. 재시도는 최초 FETCH_ERROR에만 연결하고 같은 부모에 추가 재시도를 만들지 않는다.
- 요청 본문에서 임의 URL·SQL·시설 목록을 받지 않는다. 익명·일반 사용자에게 RPC 실행 권한을 주지 않았다.

## 예약 실행 준비

- [예약 활성화 SQL](operations/enable_parking_schedule.sql): `parking-collect-5min`은 5분마다 함수 1회, `parking-purge-7days-hourly`는 정시마다 7일 초과 상태·수집 기록과 이 두 작업의 만료 실행 로그를 정리한다.
- [중지 SQL](operations/pause_parking_schedule.sql): 두 작업을 삭제하지 않고 비활성화한다.
- 확인 시 pg_cron·pg_net은 아직 미설치, Vault는 설치돼 있었다. 사용자가 A1·B1을 승인한 뒤 pg_cron·pg_net을 설치하고 두 예약 작업을 활성화했다. jobid 1은 5분 수집, jobid 2는 매시간 정리다.
- 자동 호출용 기존 default secret 키와 게이트웨이용 legacy anon JWT는 같은 프로젝트 Vault의 이름 있는 두 항목으로 보관했다. 키 값은 저장소·생성 SQL 파일·캡처·개발 기록에 넣지 않는다.
- 사용자가 A1·B1로 기존 인증정보의 같은 프로젝트 Vault 보관과 실제 7일 만료 삭제 작업 활성화를 승인했다. 두 Vault 항목 저장과 예약 작업 active=true를 확인했다. 키 값은 기록하지 않았다. 실제 만료 삭제 실행·결과는 예약 설정과 별도로 확인한다.
- 인증값을 넣은 테스트 입력은 검증 후 제거했다. 새 키 생성·키 교체·새 사용자 초대·요금제 변경은 하지 않았다.

## 예약 활성화 기록

- 사용자 `1, 1` 응답으로 A1(Vault 보관)·B1(매시간 실제 7일 만료 정리)을 승인했다.
- `parking_collector_api_key`, `parking_collector_gateway_jwt`를 같은 프로젝트 Vault에 저장했다. 비밀값은 로컬 파일에 남기지 않았다.
- `parking-collect-5min`(jobid 1, `*/5 * * * *`)과 `parking-purge-7days-hourly`(jobid 2, `0 * * * *`)의 active=true를 확인했다.
- 2026-10-23 00:33:44 KST 조회에서는 아직 첫 예약 실행 전이었다.
- 추가적인 즉시 삭제 함수 실행은 자동 승인 검토가 거절했다. 승인 범위가 예약 활성화였기 때문이며, 실제 실행되지 않았다. 우회 실행하지 않고 예약 설정·실행 이력 조회로 검증한다.
- [예약 결과 조회 SQL](checks/parking_schedule_readback.sql)은 인증값 없이 작업 이력·HTTP 결과·시설별 새 저장을 각각 확인한다.
