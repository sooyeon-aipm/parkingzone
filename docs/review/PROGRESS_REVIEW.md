## 1. 정정

사용자는 AI가 UI를 수정·검사했다는 이유로 ‘구현 학습 60%/80% 완료’라고 한 보고를 지적했다. 해당 수치를 학습·프로젝트 진행률로 철회한다. AI의 실제 코드 작성·검사 기록은 남기지만 팀의 학습·합의·검수 완료로 바꾸지 않는다. 과거 40% 역시 전체 목표의 새 기준으로 자동 재사용하지 않는다.

‘다음 단계로 진행’은 먼저 다음 단계에 필요한 질문과 추천안을 제시하고 팀이 선택하도록 돕는 뜻이다. 팀원이 같은 화면을 보고 있다는 사실만으로 검토·합의 완료를 추정하거나 질문을 생략하지 않는다. 질문은 마지막에 모으고 각 항목은 추천안 포함 3개 선택지와 직접 작성하는 기타 1개로 구성한다. 이미 합의한 정책과 UI 위치는 다시 묻지 않는다.

7번 화면의 갱신 시각과 상품명 사이 여백을 맞추라는 요청은 사용자가 취소했다. 해당 여백 수정은 적용하지 않았으며 취소된 작업을 다시 수행하지 않는다.

## 2. 확인 근거와 범위

이번 재검토는 최신 대화의 명시적 선택, TEAM_HANDOFF.md, DB_DESIGN.md, PROTOTYPE_PLAN.md, prototype/README.md와 실제 소스 파일을 대조한 문서 감사다. 이번 턴에 Chrome 동작 검사나 실제 사용자 UT를 새로 실행하지 않았다. 과거 로컬 검사 기록은 그 당시 AI 검사 기록으로만 참조한다. 노션 WBS의 현재 상태를 이번 턴에 조회하거나 변경하지 않았다.

현재 마감 목표는 ‘DB·수집 구현 설계 설명 + 최소 3개 더미데이터로 구매 전 흐름을 수행하는 프로토타입 준비’다. 실제 자동 수집·DB 저장은 기존 보류를 유지한다. 실제 사용자 UT 실행·분석, 운영 출시를 이 준비 진행도의 분모에 자동 추가하지 않는다.

DB 기본/상세 설계에서 사용자가 선택한 사항은 유지한다. 그때의 10/10, 4/4는 해당 합의 체크리스트의 완료를 뜻하며 실제 DB 구축·모든 실현 가능성 검증·팀원의 이해도를 증명하지 않는다.

## 4. 이전 질문과 사용자 선택 기록 — A2/B1/C1

프로토타입이 동작한다는 사실만으로 개선 효과를 알 수 없다. UT는 사람이 어떤 정보를 보고 어떤 이유로 선택했는지를 관찰하는 과정이다. 무엇을 알아볼지 먼저 정해야 필요한 화면·더미 상황·관찰 항목을 정할 수 있다.

기존 PRD의 운영 수집 성공률·운영 최신성·도착 시점 예측은 고정 더미 프로토타입에서 실제 운영 성과로 측정할 수 없다. 이번 UT에서는 정보 이해·선택 이유·대안 비교·과업 수행시간처럼 화면에서 실제 관찰할 수 있는 내용을 분리해야 한다. 추천은 ‘상태와 갱신 시각을 이해하고, 입차가 보장된다고 오해하지 않으면서 선택 이유를 설명하는가’를 먼저 확인하는 것이다. 사용자가 이 검증 목적을 선택했다. 상황별 과업·판정 기준은 아직 미확정이다.

A. 진행도 기준

1. 추천: 위 6개 합의·검토 항목으로 계산 — 잠정 50%, AI 작업과 구분.
2. DB 설계/프로토타입/UT 준비를 각각 따로 표시 — 전체를 하나의 숫자로 합치지 않음. 항목별 분모는 함께 정의.
3. 현재 목표에 해당하는 노션 WBS TASK 완료 비율 — 라이브 WBS 조회와 목표 TASK 선별 후 재산정, 과거 기록 제외.
4. 기타: 사용자 직접 작성.

B. 다음 학습 우선순위

1. 추천: UT 검증 질문·과업·판정 기준 — 이미 만든 화면을 왜 시험하고 무엇을 관찰할지 함께 정함.
2. 원천 갱신 시각 확보 가능성 — 실제 제공처에서 현재 상태를 판단할 근거를 확보할 수 있는지 조사. 자동 수집/DB 실행 보류를 해제하지 않음.
3. DB 상세 구현 설계의 남은 부분 — 원천 식별·저장/조회 예시·구체적인 미확정 구현 항목을 정리. 실제 DB 구축은 별도 보류.

1. 추천: 상태·시각·불확실성 이해 — 정보를 근거로 선택 이유와 판단 한계를 설명하는지 확인.
2. 선택 속도 — 같은 조건에서 선택/정보 확인 시간이 어떻게 달라지는지 확인. 빨라졌다는 사실만으로 좋은 선택이라 단정하지 않음.
3. 대안 탐색 — 처음 고른 곳이 만차/미확인일 때 다른 곳을 비교하고 선택할 수 있는지 확인.
