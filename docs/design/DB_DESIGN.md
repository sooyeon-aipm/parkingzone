# DB 상세 설계 — 학습·합의 기록

기준일: 2026-10-22. 사용자와 합의한 설계를 기록한다. 이 문서 자체는 구현 코드가 아니다. 이후 사용자가 Supabase를 선택해 기존 22개 컬럼을 실제 세 테이블로 생성하고 실DB 제약을 검사했다. 최신 구현 범위는 [Supabase 구축 기록](../../supabase/README.md)을 따른다. 아래 초기 절의 DB 제품 미정·구축 보류 표기는 당시 합의 이력이며 현재 상태와 구분한다.

진행도: 4개 묶음 중 4개 범위 합의(100%). 기본 결정과 프로젝트 범위는 [TEAM_HANDOFF.md](../history/TEAM_HANDOFF_HISTORY.md)를 따른다.

## 1. 상태 컬럼·시각·표시 — 확정

사용자가 A1 / B1 / C1을 선택했다. 다음은 DB 제품을 정하기 전의 논리 자료형이며 구체적인 SQL 타입·길이·ID 생성법은 후속 상세 정의 대상이다.

| 컬럼 | 논리 자료형 | 필수 여부 | 규칙 |
| --- | --- | --- | --- |
| id | 문자 | 필수 | 상태 기록의 고유 기본키 |
| parking_id | 문자 | 필수 | 등록된 주차장 ID를 참조하는 외래키 |
| total_spaces | 정수 | 필수 | 1 이상 |
| available_spaces | 정수 | 필수 | 0 이상, total_spaces 이하 |
| source_updated_at | 시간대가 있는 날짜·시각 | 선택 | 제공처 갱신 시각. 없으면 NULL |
| collected_at | 시간대가 있는 날짜·시각 | 필수 | 우리 수집 시각. 7일 보관 기준 |
| quality_status | 정해진 문자 코드 | 필수 | 수치·시각의 품질을 구분. 정확한 코드명은 후속 정의 |

### 시각과 품질

- 시각은 UTC 기준으로 저장하고 화면에서는 한국 시간으로 표시한다.
- 원천 갱신 시각이 없으면 수치가 정상인 기록은 저장하되 최신성 미확인으로 구분한다. 원천 시각을 우리 수집 시각으로 대체하지 않는다.
- 원천 시각이 없는 기록의 현재 혼잡도 배지 계산·표시는 보류한다.
- 이미 합의한 숫자 범위·형식 오류는 정상 상태 기록에서 제외하고 수집 오류 기록에 원본과 사유를 남긴다.
- 원천 시각이 제공됐지만 해석 불가·미래 시각인 경우의 상세 검증 규칙은 미정이다. 단순히 값이 없는 경우와 임의로 합치지 않는다.

### 최신성 — 프로토타입 임시 기준

- 조회 시각에서 원천 갱신 시각을 뺀 경과 시간이 **20분 초과**이면 오래된 정보로 판단한다. 정확히 20분인 값은 초과에 해당하지 않는다.
- 20분은 사용자 합의에 따른 프로토타입 실험값이다. 공식 기준·현장 최신성 보장이 아니며 실제 제공처의 갱신 주기 확인 후 재검토한다.
- 원천 갱신 시각이 없으면 경과 시간을 계산하지 않는다.
- ‘오래됨’은 시간에 따라 바뀌므로 조회할 때 판단한다. 보관된 품질값을 계속 수정해야 하는 것으로 설계하지 않는다.
- 상태 기록의 7일 보관과 20분 최신성 기준은 다른 규칙이다.

### 오래됨·최신 수집 실패 시 표시

- 과거 정상 기록은 7일 기한 안에서 유지한다.
- 현재 혼잡도 배지는 숨기고, ‘마지막 기록’이라는 설명과 과거 면수·그 기준 시각·주의 안내를 표시한다.
- 원천 시각이 없는 기록을 보여줄 경우 시각 미확인을 표시하며, 수집 시각을 보여준다면 ‘수집 시각’이라고 따로 표시한다.
- 최근 수집 실패 사실을 함께 안내하여 과거 기록을 현재 상태로 오인하지 않게 한다.
- 마지막 기록도 7일 기한을 넘으면 예외 없이 삭제한다. 남은 기록이 없으면 ‘최근 수집 기록 없음’을 표시한다.

## 2. 수집 기록·보관·재시도 — 확정

기존 합의: 주차장별 시도 한 번을 한 행으로 기록한다. 성공·실패는 모두 남기고 원본은 오류가 있을 때만 보관한다. 수집 기록과 오류 원본 모두 최근 7일 보관한다.

사용자가 A1/B1/C1을 선택했다. 아래는 합의한 논리 설계이며 실제 수집·삭제 작업을 실행한 것은 아니다.

| 컬럼 | 논리 자료형 | 필수 여부 | 규칙 |
| --- | --- | --- | --- |
| id | 문자 | 필수 | 수집 시도마다 고유 번호 |
| parking_id | 문자 | 조건부 선택 | 대상을 알면 등록된 주차장 ID. 대상 식별 전 실패는 NULL |
| started_at | 시간대가 있는 날짜·시각 | 필수 | 시작 시각, 수집 기록의 보관 기한 기준 |
| finished_at | 시간대가 있는 날짜·시각 | 선택 | 진행 중에는 NULL, 종료하면 기록 |
| result_status | 정해진 문자 코드 | 필수 | 진행 중·성공·접근 실패·데이터 오류. 정확한 코드명은 전체 점검에서 정리 |
| error_code | 문자 | 선택 | 오류 종류 |
| error_message | 문자 | 선택 | 사람이 읽을 수 있는 오류 설명 |
| raw_payload | 구조화된 값 또는 텍스트 | 선택 | 오류가 있을 때 원인 확인에 필요한 원본 |

### 대상 식별 전 실패의 의미

- 대상 목록을 검색·해석하는 단계에서 실패해 특정 주차장에 연결할 수 없는 경우다. 예: 성수동1가 검색 화면이 열리지 않아 시설 목록을 얻지 못함.
- 이때 parking_id는 NULL로 두고 실패 지점·검색 조건·오류 설명을 남긴다. 가짜 주차장 ID를 만들어 정상 기본정보에 등록하지 않는다.
- 이미 DEMO-001 등 대상 주차장 ID를 알고 상세 조회에 실패한 경우는 ‘대상 식별 전 실패’가 아니다. 해당 parking_id를 유지한다.
- parking_id가 있는 행은 주차장별 시도를 뜻하고, NULL 행은 특정 주차장에 귀속하지 못한 탐색 단계 실패를 뜻한다. 원래 ‘주차장별 시도’ 설계에서 합의로 추가한 예외다.

### 결과 처리

- 시도 시작을 먼저 기록하고 종료 후 결과·종료 시각을 반영한다. 도중에 중단된 시도는 성공으로 바꾸지 않는다.
- 수치 정상·원천 시각 없음은 수집 성공으로 기록할 수 있지만, 상태 기록은 최신성 미확인으로 구분한다.
- 접근 실패·수치 누락/오류는 정상 상태 기록을 추가하지 않는다. 오류 원본은 수집 기록에 남긴다.

### 재시도

- 연결 실패·응답 지연 등 접근 실패만 30초 후 1회 재시도한다. 최초 포함 최대 2회다.
- 데이터 오류는 자동 재시도하지 않는다.
- 30초 간격은 초기 설계값이며 실제 출처의 접근 조건을 확인한 뒤 재검토한다.
- 각 실제 시도는 고유한 수집 기록으로 남긴다. 재시도 간 연결 필드·중복/동시 실행 방지·중단 판정은 전체 점검에서 확인한다.

### 7일 보관·조회 제외·실제 삭제

- 상태 기록은 collected_at, 수집 시도 기록은 started_at 기준으로 현재 시각에서 7일을 초과하면 조회에서 제외한다.
- 실제 DB 삭제는 매시간 실행한다. 정상 실행 중에도 만료 직후부터 삭제까지 약 1시간의 지연이 생길 수 있다는 조건을 설명한 뒤 사용자가 선택했다.
- 오류 원본은 해당 수집 기록과 같은 보관·삭제 규칙을 따른다. 기본정보는 시간 경과만으로 자동 삭제하지 않는다.
- 실제 자동 수집·DB 저장의 실행 범위는 기존 사용자 보류 상태다. 이번 합의가 운영 자동화 구현 요청을 뜻하지 않는다.

## 3. 화면 조회 JSON·더미 예시 — 확정

사용자가 A1(목록·상세 공통 양식), C1(고정 테스트 시각·초기화), 이어서 B1(15개 전체 기본정보와 테스트용 가상 현황)을 선택했다. 실제 이름·주소 원문은 [PARKING_SOURCE_LIST.md](PARKING_SOURCE_LIST.md)에 보존했다. 현황 수치·시각·원천 ID는 제공되지 않았고 AI가 현재 상태를 재조회한 것은 아니다.

15개 전체에 가상 현황을 연결하고, 5단계·정상·시각 없음·오래됨·수집 실패·검색 결과 없음을 재현한다. 시설명·주소는 사용자 제공 자료이고 면수·시각·상태는 테스트용 가상값이라는 안내를 표시한다. 실제 현황 수집·구현 완료로 보고하지 않는다.

### 공통 조회 양식 제안

DB의 세 테이블과 화면에서 받는 양식은 같을 필요가 없다. 합의한 A1에 따라 저장은 목적별로 나누고, 화면은 한 주차장의 기본정보·마지막 유효 수치·최신 수집 결과·표시 판정을 모아 받는다. 목록과 상세는 같은 주차장 데이터를 사용한다. error raw_payload와 내부 오류 원문은 사용자 화면에 전달하지 않는다.

| 묶음 | 내용 | 저장/계산 구분 |
| --- | --- | --- |
| data_origin, as_of | 더미 여부·판정 기준 시각 | 테스트 메타정보·조회 기준 |
| parking | id·이름·주소 | 기본정보에서 조회 |
| latest_record | 마지막 유효 면수·원천 시각·수집 시각. 없으면 NULL | 7일 안의 상태 기록에서 조회 |
| latest_collection | 최신 수집 결과·시도 시각 | 수집 기록에서 조회 |
| freshness | 최신/오래됨/원천 시각 미확인/기록 없음, 경과 분 | 조회 시 계산 |
| display | 현재/마지막 기록/정보 없음 구분·배지·안내 | 공통 규칙으로 계산, DB 저장 컬럼 아님 |

상태와 수집 결과·최신성을 별도 항목으로 전달한다. 예를 들어 이전 수치는 5분 전 값이어도 최신 수집이 실패했다면 freshness와 실패 안내를 모두 보존하고, 합의대로 현재 배지 대신 마지막 기록을 표시한다. 최신 기록의 원천 시각이 없는데 더 오래된 기록을 몰래 골라 최신인 것처럼 보여주지 않는다.

아래 문자열 코드와 JSON 키의 구체적인 명칭은 이 묶음의 제안이다. 가상 테스트 기준 시각은 2026-10-22 12:00 한국 시간이다.

```json
{
  "data_origin": "DEMO",
  "as_of": "2026-10-22T03:00:00Z",
  "parking": {
    "id": "DEMO-001",
    "name": "성수 테스트 A",
    "address": "성수동1가 가상 주소 A"
  },
  "latest_record": {
    "total_spaces": 100,
    "available_spaces": 80,
    "source_updated_at": "2026-10-22T02:55:00Z",
    "collected_at": "2026-10-22T02:56:00Z"
  },
  "latest_collection": {
    "result": "SUCCESS",
    "attempted_at": "2026-10-22T02:56:00Z"
  },
  "freshness": {
    "state": "FRESH",
    "age_minutes": 5
  },
  "display": {
    "mode": "CURRENT",
    "congestion_label": "여유",
    "notice": "갱신 시점 기준 정보이며 도착 시점의 자리는 보장되지 않아요."
  }
}
```

### 초기 가상 시설 예시 — 실제 시설 목록으로 교체 검토

아래 A/B/C 가상 시설은 공통 양식 학습을 위한 초기 예시다. 현행 기본정보 후보는 사용자 제공 15개 실명 시설이며, 아래 가상 이름을 기본정보로 확정한 것이 아니다. 아래 100면 등의 숫자도 실제 시설 규모가 아닌 가상 계산 예시다.

| 가상 시설 | 전체/가능면수 | 기본 상태 |
| --- | --- | --- |
| DEMO-001 성수 테스트 A | 100/80 | 점유율 20%, 여유 |
| DEMO-002 성수 테스트 B | 100/30 | 점유율 70%, 혼잡 |
| DEMO-003 성수 테스트 C | 100/0 | 점유율 100%, 만차 |

- 같은 시설의 테스트 데이터를 바꿔 보통(100/50), 매우혼잡(100/10)을 재현하는 안을 추천한다.
- 예외는 원천 시각 없음, 20분 초과, 최신 수집 실패, 기록 없음/7일 초과, 검색 결과 없음, 잘못된 수치로 나눈다. 검색 결과 없음은 상태를 바꾸는 것과 달리 검색 조건으로 발생시킨다.
- 잘못된 수치를 주입하는 시험은 검증 오류 경로로 보내며 정상 상태 기록으로 반영하지 않는다.
- 가상 데이터·테스트 기준 시각·모드 전환은 테스트 진행자용으로 구분하고, 참가자에게는 테스트 데이터임을 안내한다. 실제 현황·수집 운영으로 표현하지 않는다.
- C1 합의에 따라 고정된 테스트 시각과 초기화 기능을 사용한다. 반복 UT의 조건을 같게 할 수 있지만 실제 시각 경과 시험을 대신하지는 않는다. 코드 예시의 특정 시각은 설명용이며 실제 현황 갱신 시각이 아니다.

### 이 묶음의 확인 질문

- A1 확정: 공통 양식으로 모아 목록·상세에 전달한다.
- B1 확정: 사용자 제공 15개 전체의 기본정보에 가상 현황을 붙이고 상태·예외 시나리오를 배치한다.
- C1 확정: 고정 테스트 시각과 초기화 기능을 사용한다.

A/B/C를 합의해 3묶음 설계 검토를 완료했다. 실제 더미데이터·조회 함수·프로토타입을 구현한 것은 아니다.

## 4. 전체 컬럼표·관계·누락 점검 — 범위 합의 완료

기본정보·상태·수집 기록의 관계, 보관 기한과 외래키 제약, 실패·중복·삭제 흐름, 화면에서 사용할 데이터와 설계 설명을 함께 점검한다.

사용자가 A1(연결 컬럼 2개·중복 방지·보관 시 연결 처리), B1(잘못된 시각 오류 처리·필요한 원본만 보관)을 선택했다. 아래 A·B는 합의 내용이다. C는 사용자 스케치 대조 후 모바일 웹·상호작용 예시 지도·같은 가상 상품 데이터의 기존안/개선안 모드로 합의했다. 상세 검토안은 [PROTOTYPE_PLAN.md](PROTOTYPE_PLAN.md)를 따른다.

### A. 연결·중복 방지 — 확정

- 기존 기본정보 5개, 상태 7개, 수집 8개 컬럼에서 시작한다. A1 합의에 따라 내부 ID는 UUID 형태의 문자로 생성하고 원천 ID는 임의 생성하지 않는다.
- 상태에 collection_attempt_id를 선택 외래키로 1개 추가해 어느 수집 시도에서 나온 값인지 연결한다. 한 수집 시도에는 최대 한 상태 기록만 연결되도록 중복을 막는다. 새 수집 시도에서 같은 원천 값이 다시 읽힌 경우와 같은 시도가 중복 저장된 경우를 구분한다.
- 수집 기록에 retry_of_id를 선택 외래키로 1개 추가해 재시도와 최초 시도를 연결한다. 재시도는 별도 ID로 기록하고, 같은 주차장의 수집이 겹쳐 실행되지 않도록 하는 안이다.
- 서로 다른 보관 기준 시각 때문에 수집 기록이 상태 기록보다 먼저 만료될 수 있다. 수집 기록 삭제 시 상태의 collection_attempt_id만 NULL로 바꾸고 상태 자체는 collected_at 기준 7일까지 유지한다. 재시도 부모가 먼저 삭제되면 retry_of_id도 NULL로 바꾼다. 주차장 기본정보까지 연쇄 삭제하지 않는다.
- 주차장 기본정보는 연결된 상태 또는 수집 기록이 남아 있으면 삭제를 제한한다. 이름 변경만으로 새 시설을 만들거나 이름만으로 자동 합치지 않는다. 초기 15개 시설은 사용자 목록과 대응한 고정 기본정보로 관리하고, 원천 ID 확보 후 연결 근거를 확인한다.
- A1 선택으로 상태 8개·수집 9개 컬럼이 되는 변경을 합의했다. 1·2절의 표는 최초 7개·8개 컬럼이며 이 절의 추가 컬럼과 연결 규칙을 합쳐 현재 설계로 사용한다.

### B. 코드·시각 오류·원본 보관 — 확정

| 구분 | 코드 제안 | 의미 |
| --- | --- | --- |
| 상태 품질 | VALID | 수치와 원천 갱신 시각이 유효함. 조회 시 최신성을 별도 판단 |
| 상태 품질 | SOURCE_TIME_MISSING | 수치는 정상이나 원천 갱신 시각이 없음 |
| 수집 결과 | IN_PROGRESS | 시작했고 아직 종료되지 않음 |
| 수집 결과 | SUCCESS | 정상 수치를 확보함. 원천 시각 없음은 상태 품질로 구분 |
| 수집 결과 | FETCH_ERROR | 접근·응답 실패 |
| 수집 결과 | VALIDATION_ERROR | 필수 수치·범위·원천 시각 해석 오류 등 |
| 수집 결과(후속 확정) | SOURCE_UNAVAILABLE | 사용자 선택으로 추가. 요청은 성공했지만 원천 미연계·정보수집중·통신점검 등으로 정상 수치를 사용할 수 없음 |

- 원천 시각 없음은 합의대로 저장한다. 원천 시각 값이 있지만 해석 불가하거나 collected_at보다 미래라면 정상 상태로 반영하지 않고 데이터 오류 기록에 남기는 안이다. 시각 오차 허용 범위는 이번 프로토타입에서 두지 않는 초안이다.
- 오류 원본은 추출값·출처·실패 단계·오류 확인에 필요한 최소 내용만 남기고 전체 HTML·스크린샷의 자동 보관은 이번 범위에서 제외하는 안이다. 비밀번호·토큰 등 비밀값은 기록하지 않는다.
- 오래됨은 품질 코드에 고정 저장하지 않는다. 수치가 유효하고 VALID여도 조회 시 원천 갱신 후 20분이 지났으면 오래됨으로 표시한다.
- IN_PROGRESS가 남은 기록은 성공으로 간주하지 않는다. 실제 운영의 타임아웃·중단 판정 기준과 공급처별 수집 주기는 제공처 검증 후 정할 운영 항목으로 분리한다.

### C. 구현 경로 — 확정

단순 현황 조회 서비스 형태보다 기존 앱의 지도→주차권 비교→선택→상세·구매 전 확인 맥락을 재현하는 모바일 웹을 추천한다. 러프 스케치를 픽셀 단위로 복제하지 않는다. 사용자가 C1/D1/E1을 선택했다. 상호작용 예시 지도, 공통 가상 상품 정보, 기존안/개선안 모드를 사용한다. 구현은 팀원 설명·확인 단위로 나눠 진행한다.

- 빠른 학습·시연을 위해 HTML/CSS/JavaScript와 로컬 JSON으로 동작 프로토타입을 만드는 안을 추천한다. 화면 구성·시나리오·핵심 함수 단위로 설명하고 팀원 확인을 받으며 진행한다.
- 목록·검색·상세·재선택, 15개 테스트 현황, 상태·예외 전환, 초기화 기능부터 준비한다. 원본 오류·수집 제어는 참가자용 화면과 분리한다.
- DB 관계도·컬럼 정의서·저장/조회/삭제 흐름은 문서 산출물로 준비한다. 실제 DB 생성·자동 수집 운영은 기존 보류를 유지한다. 이 경로에서 SQL의 특정 DB 엔진 방언이 확정됐다고 표현하지 않는다.
- 실제 DB 제품별 SQL 타입·길이·공급처 운영 타임아웃 등은 미정으로 남긴다. 100%는 네 묶음 범위 선택 완료이며 실제 DB·프로토타입·운영 검증 완료를 뜻하지 않는다.
