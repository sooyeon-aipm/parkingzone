# 모두의주차장 개선 프로젝트 — 팀원 로컬 작업 인수인계

DB 기본 설계 합의만 기존 4/4 기준 100%이며 프로토타입 최종 검토·UT 준비는 분모/완료 근거 확정 전 산정 대기다. ‘다음 단계’는 먼저 필요한 질문을 제시한다는 뜻이다. [진행도 기준·근거·다음 질문](../review/PROGRESS_REVIEW.md)을 먼저 읽는다. 취소된 상세 여백 수정은 적용하지 않는다.

## 0. 최신 DB 학습 결정 — 기초 검토 10/10 완료

### 최신 목표·진행 방식

- 10월 22일 18시까지 설계 설명과 더미데이터 동작 프로토타입을 준비하는 것을 사용자가 이상적인 앞당긴 목표로 제시했다. 기존 10월 23일 14시 목표를 취소한 것은 아니다.
- 관련 설계·학습 항목은 묶어 설명하고, 결정이 필요한 질문만 마지막에 모은다. 질문마다 추천안·대안 2개·직접 작성하는 기타로 총 4안을 유지한다.
- 상세 설계 진행도는 4개 묶음의 확정 여부로 표시한다: ① 상태 컬럼·시각·표시 ② 수집 기록·보관·재시도 ③ 화면 조회 JSON·더미 예시 ④ 전체 컬럼표·관계·누락 점검. 현재 4/4 범위 합의(100%)이다. 기초 학습 100% 및 전체 제품 구현률과 구분한다.
- 첫 묶음은 A1/B1/C1로 합의했다. 원천 시각 없으면 NULL·최신성 미확인으로 저장하고 현재 배지는 표시하지 않는다. UTC 저장·한국 시간 표시, 원천 갱신 후 20분 초과 시 오래됨(프로토타입 임시값), 지연·최신 수집 실패 시 현재 배지 대신 ‘마지막 기록’·면수·시각·주의 안내를 표시한다. 상세는 [DB_DESIGN.md](../design/DB_DESIGN.md)를 따른다.
- 둘째 묶음도 A1/B1/C1로 합의했다. 수집 시작·종료·결과를 기록하고, 대상 식별 전 실패는 parking_id=NULL로 보존한다. 이미 대상을 알면 그 ID를 기록한다. 접근 실패만 30초 후 1회 재시도(최초 포함 2회), 데이터 오류는 자동 재시도하지 않는다. 수집 기록 보관은 started_at 기준 7일, 상태는 collected_at 기준 7일이며, 기한 초과 기록은 조회 제외하고 매시간 실제 삭제한다. 삭제까지 약 1시간 지연될 수 있는 조건을 포함한 합의다.
- 셋째 묶음은 A1(공통 양식), C1(고정 테스트 시각·초기화), B1(사용자 제공 15개 전체 기본정보+가상 현황)을 합의했다. 원문과 확인 범위는 [PARKING_SOURCE_LIST.md](../design/PARKING_SOURCE_LIST.md)를 따른다. 75%는 설계 검토 진행도이며 실제 수집·조회 함수·화면을 구현한 것은 아니다.
- 마지막 묶음 A1·B1을 합의했다. 상태에 collection_attempt_id, 수집에 retry_of_id를 추가하고 중복·보관 만료 시 연결만 비우는 규칙을 적용한다. ID는 UUID 문자형, 잘못된 원천 시각은 데이터 오류, 원본은 필요한 내용만 보관한다. C 구현 경로는 후속 C1/D1/E1 선택으로 합의했다. HTML/CSS/JavaScript 모바일 웹, 상호작용 예시 지도, 동일 가상 상품 데이터의 기존안/개선안 모드를 사용한다. 사용자는 앱_플로우/개선 앱플로우의 러프 스케치처럼 기존 앱의 구매 전 흐름을 개선한다고 명확히 했다. 관련 6개 스케치·기존 대응 화면·기록을 확인한 제안은 [PROTOTYPE_PLAN.md](../design/PROTOTYPE_PLAN.md)에 정리했다.

답변 첫 줄에는 진행도를 표시한다. 현재 **DB 기초 설계 학습 100%**이며, 실제 DB 구현률이나 프로젝트 전체 진행률이 아니다. 10개 항목은 데이터 분리 / 상태 보관 / 기본키 / 기본 컬럼 / 기본정보 자료형·필수값 / 상태 컬럼 / 테이블 관계 / 수치 검증 / 수집 기록 / 전체 점검이다. 세 테이블의 역할과 기본 정책을 점검해 기초 체크리스트를 마쳤다. 상세 명세·실현 가능성 확인·구현은 남아 있다.

아래는 이 문서 작성 이후 사용자 선택으로 합의한 내용이다. 뒤쪽의 첫 실습·HTML에 남아 있는 초기 DB 제안보다 아래 결정이 우선한다. 실제 DB·SQL·자동 수집은 구현하지 않았다. 이후 prototype/에 한 시설의 첫 화면 동작을 구현했고 현재 상황은 아래 구현 기록을 따른다.

### AI 구현·점검 현황 — 팀 학습 진행률과 구분

- 사용자는 기존 서비스처럼 보이도록 `앱_플로우/앱캡처`를 기준으로 다시 만들라고 요청했다. 기존 단순 예시보다 원본 앱의 화면·구매 전 흐름 재현을 우선한다.
- [prototype/README.md](../../prototype/README.md)에 화면 범위·실행법·학습 포인트·검증·한계를 기록했다. 15개 시설 검색·정렬·목록→상세 축약/펼침→복귀를 연결했다. 상태 5단계·예외 선택·기존안/개선안·초기화도 연결했지만 팀 검토와 재현 점검이 남아 전체 완료로 세지 않는다.
- 사용자는 ‘구매하기’ 1안(선택 결과를 로컬에 기록하고 테스트 종료)을 승인했다. 실제 결제·예약 없이 브라우저 localStorage에 저장한다. 새로고침 후 기록 유지를 확인했다. 현재 Chrome의 1건은 AI 기능 점검이며 실제 사용자 UT가 아니다.
- 지도는 승인된 A1/B1에 따라 성수동 Kakao 일반 지도 캡처+가상 표식으로 교체했다. 일반 주차권 구매 전 흐름까지이며 실제 시설 좌표·거리는 검증하지 않았다.
- REA 연결 제안을 받았으나 설치·MCP 설정 변경은 하지 않았다. 화면 복제 자동화 도구로 간주하지 않는다. 캡처에 없는 동작은 실제 앱 관찰 또는 별도 분석이 필요하다.
- JSON→model.js 공통 판정→app.js 화면 선택 순서로 팀원이 읽는다. AI가 만든 동작을 팀 검토·학습·실사용자 UT의 완료로 간주하지 않는다.
- 실제 DB·자동 수집·로그인·운영 상품·배포는 연결하지 않았다. Chrome 실제 정보 관찰은 research/source-observations/에 분리하며 고정 가상 UT 데이터와 섞지 않았다.

### 합의한 구조와 규칙

- 기본정보와 시점별 상태 기록을 나누며, 새 상태는 덮어쓰지 않고 별도 행으로 추가한다.
- 기본정보의 `id`는 우리가 만든 UUID 문자형 고유 ID를 기본키로 사용한다. 원천 시설 ID와 구분한다.
- 기본정보 컬럼은 `id`, `name`, `address`, `source`, `source_parking_id` 5개다. 모두 문자형이며 `source_parking_id`만 NULL을 허용한다. 나머지는 필수이고 `id`는 중복 불가다.
- 상태는 최초 7개 컬럼에 collection_attempt_id를 추가해 현재 8개 컬럼이다. 수집은 최초 8개 컬럼에 retry_of_id를 추가해 9개다. 상세는 DB_DESIGN.md 1·2·4절을 함께 따른다. SQL 자료형의 구체적인 방언·길이는 구현 DB 선택에 맞춰 정의한다.
- 점유율과 5단계 혼잡도는 원본 면수로 조회 시 계산한다. 별도 저장하지 않는다. 과거 판정 당시의 정책 버전·결과 보존은 이번 범위에서 합의하지 않았다.
- 기본정보의 `id`와 상태의 `parking_id`를 외래키로 연결한다. 주차장 하나에 상태 기록 여러 개가 연결되는 일대다 관계다.
- 등록된 주차장에만 상태 기록을 추가하고, 상태 기록이 남아 있으면 기본정보 삭제를 제한한다. 상태 기록만 삭제해도 기본정보는 유지한다.
- 현재 시각에서 우리 수집 시각 `collected_at` 기준 **7일 초과 상태 기록을 예외 없이 조회 제외·삭제**한다. 마지막 정상 기록도 예외가 아니다. 남은 기록이 없으면 ‘최근 수집 기록 없음’을 표시한다. 실제 삭제는 합의대로 매시간 수행하며 실제 구현은 아직 하지 않았다.
- 전체면수는 1 이상의 정수, 가능면수는 0 이상의 정수이며 전체면수를 넘을 수 없다. 누락값을 0으로 바꾸지 않는다.
- 잘못된 수치는 정상 상태 기록에서 제외하고 별도 수집 기록에 원본과 사유를 남긴다. 실패 시 마지막 정상 기록은 덮어쓰지 않되, 7일 보관 규칙은 유지한다. 과거 정상값을 최신처럼 표시하지 않는다.
- 수집 기록은 **주차장별 시도 한 번을 한 행**으로 기록한다. `id`, `parking_id`, `started_at`, `finished_at`, `result_status`, `error_code`, `error_message`, `raw_payload`를 출발 컬럼으로 채택했다. 결과 상태 목록·자료형·필수값은 추가 정의가 필요하다.
- 성공·실패 시도는 기록하고, `raw_payload`는 오류가 있을 때 보관한다. 원본의 구체적인 형식·범위·크기 제한은 미정이다. 전체 HTML·화면을 매번 저장하기로 정한 것은 아니다.

### 추가 합의: 수집 기록 보관

수집 시도 기록과 오류 원본도 최근 7일만 보관하고, 기한 초과 시 삭제한다. 보관 기간을 계산할 구체적 시각 컬럼과 삭제 실행 주기는 상세 설계에서 정한다.

### 상세 설계에서 남은 부분
- 상태·수집 테이블의구체적인 SQL 타입·길이, 원본 크기 제한·운영 타임아웃 기준 등 실제 수집 검증이 필요한 상세값.
- 구매 버튼은 로컬 선택 기록·테스트 종료로 승인되어 구현했다. 지도는 성수동 캡처 배경+가상 표식으로, 범위는 일반 주차권 구매 전까지로 확정했다. C 구현·지도·가상 상품·비교 모드의 범위는 합의했다. 실제 수집·DB 저장은 기존 보류를 유지한다.

기초 학습 체크리스트를 마쳐도 위 상세 정의와 실제 구현 가능성 검증이 남는다. ‘학습 100%’를 ‘DB 상세 설계·개발 완료’로 보고하지 않는다.

4. [wbs-review.html](wbs-review.html): 마감 기준 우선순위·완료 기준·분담 제안을 보기 쉽게 정리한 검토안.

이후 팀에서 새로 결정한 내용은 결정일·결정자·근거와 함께 반영한다. 문서끼리 충돌하면 최신의 명시적 사용자 결정과 팀 결정을 확인하고, 새 결정을 임의로 만들지 않는다.

## 2. 팀 운영 방식

- 대표: 수연. 프로젝트 리드, 과제 제시, 학습 지원과 피드백을 맡는다.
- 팀원: 유미, 종현. 회의하며 과제를 수행하고 결과와 질문을 공유한다.
- 주 2~3회 회의에서 피드백을 받고 다음 단계로 진행한다. 구체적인 회의 일정은 이 문서에서 확정하지 않는다.
- 아래 유미·종현의 역할 분담은 제안이다. 실제 노션 담당자를 새로 배정한 것은 아니다.

AI는 팀원을 학습시키며 제안하는 협업자다. 설계·코드를 혼자 완성한 뒤 결과만 전달하지 않는다.

진행 순서:

1. 관련 개념·설계 규칙을 묶어 쉬운 말로 짧게 설명한다.
2. 작은 예시와 추천안, 이유·한계를 제시한다.
3. 팀원이 초안이나 판단 이유를 작성한다.
4. AI가 초안의 문제·이유·확인 방법을 설명한다.
5. 팀이 결정한 내용을 반영하고 다음 단계로 간다.

이미 합의한 내용은 반복 질문하지 않는다. 확인할 내용과 새로운 충돌은 독립 작업을 진행한 뒤 마지막에 모아 질문한다.

**각 질문은 반드시 총 4안으로 구성한다.**

1. 추천안과 짧은 추천 이유
2. 대안과 차이
3. 다른 대안과 차이
4. 기타: 사용자가 직접 작성할 수 있는 빈칸

답변이 없다고 동의로 처리하지 않는다. AI가 제시한 테이블·컬럼·수치·담당·일정은 명시적으로 합의되기 전까지 제안으로 표시한다.

## 3. 프로젝트와 이번 목표

주차권을 구매하고 방문했지만 만차 등으로 주차하지 못하는 문제를 줄이기 위해, 구매 전에 현재 상태·정보 기준 시각·불확실성을 확인하고 주차장을 선택할 수 있도록 개선한다.

프로젝트의 최종 방향은 **모두의주차장 구매 전 화면 개선 프로토타입 + 기존안·개선안 비교 UT + 최종 제안서**다. UT는 실제 사용자가 과제를 수행하게 하여 동작·정보 이해·선택 경험을 확인하는 사용자 테스트다.

**이번 우선 목표: 2026-10-23 14:00까지 다음을 준비한다.**

최신 추가 목표는 2026-10-22 18:00까지 아래 결과물을 앞당겨 준비하는 것이다. 이는 이상적인 목표이며 완료 예측이나 구현 완료 보고가 아니다.

- DB 설계: 테이블의 목적과 관계, 식별·중복·이력 처리 설명.
- 데이터 컬럼 정의: 의미, 자료형, 필수 여부, 출처, 계산·검증 규칙, 예시.
- 수집부터 화면까지 어떻게 구현할지 설명하는 설계.
- 최소 3개 더미 주차장 데이터로 UT가 가능할 정도로 동작하는 프로토타입.

이번 마감은 실제 UT 실행이나 최종 제안서 완성까지 요구한 것이 아니다. 가용 작업시간과 중간 회의 시각은 미확인이다.

## 4. 공공 API에서 화면 수집으로 바꾼 이유

원래 공공데이터 API를 사용하려 했지만 API로 확보할 수 있는 대상 주차장 범위가 적어서 화면 수집 방향으로 전환했다. **API가 실시간 정보를 전혀 제공하지 않는다는 뜻은 아니다.**

- 현재 출처: [서울특별시 주차정보안내시스템](https://parking.seoul.go.kr/).
- 반복 실행은 AI가 작성한 자동화 코드로 할 수 있는지 우선 검토한다. 매번 AI가 화면을 읽는 방식으로 확정하지 않는다.
- 주소·실시간 제공 여부로 포함 대상을 판단한다. 이름이나 검색어 일치만으로 대상을 확정하지 않는다.
- 화면의 시설 식별자·전체면수·가능면수·원천 갱신 시각 제공 여부는 확인이 필요하다.
- API의 `PKLT_CD` 같은 원본 필드가 화면 수집에서도 그대로 제공된다고 가정하지 않는다.
- 수집 방식의 이용 조건·접근 제약은 구현 방식 검토에 포함한다. 자동 수집이 이미 가능하거나 운영 중인 것으로 보고하지 않는다.

## 9. 용어: 원천 갱신 시각과 수집 시각

**원천 갱신 시각**은 정보를 제공하는 쪽에서 표시·제공한 ‘그 주차 상태가 갱신된 기준 시각’이다. ‘원천 시각’이라고 줄여 부른 표현은 모호하므로 앞으로 원천 갱신 시각이라고 쓴다.

**수집 시각**은 우리 프로그램이 그 정보를 읽어온 시각이다.

가상 예시:

- 제공처 상태 갱신: 10:00, 가능면수 12면.
- 우리 프로그램 수집: 10:07, 같은 12면을 읽음.
- 원천 갱신 시각은 10:00, 수집 시각은 10:07이다.
- 다시 10:10에 읽어도 제공처가 갱신되지 않았다면 원천 갱신 시각은 여전히 10:00이다.

수집을 방금 했다는 사실만으로 현장 상태도 방금 갱신되었다고 말할 수 없다. 제공처 갱신 시각이 없으면 `null` 또는 미확인으로 두고 우리 수집 시각으로 대체하지 않는다. 실제 출처에서 그 시각이 무엇을 의미하는지도 확인해야 한다. 홈페이지의 ‘정보 등록/수정일’이 실시간 상태 갱신 시각이라는 뜻은 아니다.

## 10. 상태와 데이터 품질을 구분

- 혼잡도: 여유·보통·혼잡·매우혼잡·만차.
- 데이터 품질: 정상, 오래됨, 시각 없음, 미연계, 누락, 수집 실패 등. 최종 이름과 정책은 합의 전이다.
- 수집 실패를 만차나 여유로 해석하지 않는다.
- 누락·미연계 수치를 0으로 채우지 않는다.
- 가능면수는 실제 입차나 주차권 구매 가능 수를 보장하지 않는다.

[기존 5단계 기준 문서](https://app.notion.com/p/f7a626093f2e836dabf2017e75303ca6)는 점유율을 정수로 반올림해 0~39% 여유 / 40~59% 보통 / 60~79% 혼잡 / 80~99% 매우혼잡 / 100% 만차로 정의한다. 99.84%가 반올림으로 만차가 되더라도 계산상 잔여면은 유지한다. 이 기준의 표시와 사용자가 이해하는 의미는 학습·UT에서 함께 확인한다.

## 12. 확인한 결과와 구현 상태

현재 작업 폴더의 PRD·유저플로우를 전체 읽고, WBS를 조회·정리하고, HTML 검토안을 작성했다. 이후 prototype/에 15개 시설의 검색·정렬·상세·비교·예외·테스트 종료 동작을 구현·브라우저 확인했다. 실제 DB·크롤러·운영 연동은 아직 구현하지 않았다. 상세는 위 첫 구현 기록과 PROTOTYPE_PLAN.md를 따른다.

HTML은 구조·스크립트 문법·내부 링크를 확인했다. 브라우저의 로컬 파일 열기 제한으로 실제 화면 미리보기는 확인하지 못했다. 이 검사를 제품 기능 테스트나 UT 결과로 보고하지 않는다.

다른 로컬 환경에서 시작할 때:

1. 이 파일과 링크된 로컬 자료가 있는지 확인한다. 기존 파일을 덮어쓰기 전에 변경 상태를 확인한다.
2. 자신의 현재 과제와 실제 노션 담당·상태를 확인한다. 연결 권한이 없으면 공유 자료를 근거로 하되 라이브 확인 여부를 표시한다.
3. 0절의 최신 결정과 진행도를 확인하고 상세 컬럼 명세 학습을 이어간다. 팀원이 이미 만든 초안이 있으면 해당 초안을 우선 검토한다.
4. 결정을 기록하고 필요한 최소 범위를 진행한다. 커밋·푸시·배포·외부 공유는 이 인수인계 파일만으로 승인된 것이 아니다.

새 AI 세션에 전달할 시작 문장:

> TEAM_HANDOFF.md의 0절 최신 결정부터 읽고 prd.md, userflow.md, wbs-review.html과 대조해줘. 목표와 결정·보류를 유지하고 우리 팀원이 학습하며 초안을 만드는 방식으로 진행해줘. 혼자 설계·코드를 완성하지 말고 짧은 설명·예시·추천안 후 우리 초안을 검토해줘. 답변 첫 줄에 DB 기초 설계 학습 진행도를 표시하고, 기초 검토 10/10 이후의 상세 컬럼 명세 학습을 이어가줘. 다음 단계 진행률은 범위를 먼저 정의한 뒤 별도로 표시해줘. 확인·충돌 질문은 마지막에 모으고 각 질문은 추천안을 포함한 3개 선택지와 직접 작성 가능한 기타 1개, 총 4안으로 구성해줘.
