# 23일 과제 — 팀 최종 검토표

기준일: 2026-10-22. 사용자 보고로 유미·종현의 기존 결과물 확인을 기록했다. 수연 검토는 대기다. 아래 체크는 수연 검토 시 참고할 표이며 AI가 대신 최종 승인하지 않는다. [검토 요청 묶음](SUYEON_REVIEW.md)을 따른다.

기본 산출물은 준비되어 있다. 실제 DB 제품/SQL 구체화·실제 수집 실행·원천 ID/갱신 시각의 실제 확보 등 미정/보류 사항이 있다는 사실을 산출물 전체가 없다는 뜻으로 해석하지 않는다. 실행 가능성의 모든 세부 검증까지 끝났다는 뜻도 아니다.

## 2. 설계를 설명하는 순서

### 저장할 것 세 가지

- 기본정보: 주차장 자체의 이름·주소·출처. `id`는 우리 시설 고유 번호이며 `source_parking_id`는 실제 출처의 시설 ID를 확인하기 전까지 NULL이다.
- 상태 기록: 그 주차장의 시점별 면수·원천 갱신 시각·수집 시각. `parking_id`로 기본정보를 참조한다. 한 시설에 여러 시점의 기록이 연결된다.
- 수집 시도: 읽기 시작·종료·성공/실패·오류 사유. 같은 시설을 다시 읽는 것은 새 시도다. 상태의 `collection_attempt_id`가 그 기록을 만든 시도에 연결되고, `retry_of_id`는 재시도와 최초 시도를 연결한다.

최초 컬럼표 뒤에 추가한 연결 컬럼까지 포함해야 한다. 최종 기본정보 5개, 상태 8개, 수집 9개 컬럼이다. 초기 표의 7개/8개만 최종 정의라고 읽지 않는다.

### 구현 흐름

1. 성수동1가·성수동2가의 대상 시설을 우리 ID와 연결한다. 원천 식별자가 확인되지 않았으면 임의 생성해 실제 제공처 ID라고 쓰지 않는다.
2. 수집 코드가 시도 시작을 기록하고 제공처 화면을 읽는다. 이 단계는 설계이며 현재 자동 실행 중인 것이 아니다.
3. 전체/가능면수와 시각을 검증한다. 수치 오류·잘못된 시각은 정상 상태로 만들지 않고 오류 시도에 사유를 남긴다. 원천 시각 없음은 값 오류와 구분한다.
4. 유효 수치면 시점별 상태를 추가한다. 실패 시 과거 정상값을 새 현재값으로 덮어쓰지 않는다.
5. 화면 조회 시 보관 기한·최신성·최근 수집 결과를 확인하고 5단계 배지/마지막 기록/정보 없음을 결정한다. 원천 갱신 시각과 우리 수집 시각을 바꾸어 쓰지 않는다.
6. 상태는 collected_at, 수집 기록은 started_at 기준 7일 초과분을 조회 제외하고 설계상 매시간 실제 삭제한다. 현재 프로토타입이 실제 DB 정리 작업을 실행하는 것은 아니다.

설명 확인 질문: ‘언제 읽었는가’와 ‘언제 갱신된 상태인가’는 왜 다른가? ‘조회 실패’가 왜 ‘만차’나 ‘가능 0면’이 아닌가? 답을 암기했는지보다 예시에서 어떤 정보를 유지/숨기는지 팀이 설명할 수 있는지 확인한다. 기존 합의를 새로 선택하라는 질문이 아니다.

- [ ] 세 테이블과 ID 연결을 팀이 설명할 수 있다.
- [ ] 정상·시각 없음·조회 실패·7일 보관 흐름을 설명할 수 있다.
- [ ] 미정/보류가 무엇인지 실제 구현 완료와 구분해 설명할 수 있다.

## 3. 핵심 화면 직접 확인

서버가 실행 중이면 http://127.0.0.1:8765/?layout=1 을 연다. 프로토타입 판단 시각은 고정 12:00 KST다. 아래 수치는 강변 예시의 가상값이며 실제 주차 현황이 아니다.

| 진행자 선택 | 기대되는 표시 | 팀이 확인할 것 |
| --- | --- | --- |
| 정상 | 목록 ‘여유·갱신 11:55’, 상세 가능 80/전체 100 | 목록 배치 1안, 상세 혼잡도+이름 한 줄, 갱신 시각 아래 중앙 |
| 갱신 지연 | 현재 배지 대신 ‘확인 필요’, 갱신 11:30 | 상세에 마지막 기록 80/100과 최신 정보 아님 안내 |
| 원천 갱신 시각 없음 | 목록 ‘확인 필요·미확인’ | 상세에 원천 시각 미확인, 현재 상태로 단정하지 않음 |

- [ ] 목록에서 시설 선택→상세 축약/펼침→목록 복귀가 가능하다.
- [ ] 위 세 상황을 현재 사용할 환경에서 확인했다.
- [ ] 가상 지도 표식·거리·상품·현황을 실제 운영 정보로 오해하지 않는다.
- [ ] 구매하기가 선택 기록 후 테스트 종료로 이어진다. 실제 결제·예약이 아니다.
- [ ] 처음으로는 화면 조건을 초기화하고 기록을 지우지 않는다.

위 목록은 최종 팀 확인용이다. 과거 AI의 기능 점검 기록은 prototype/STATE_REVIEW.md와 COMPARE_REVIEW.md에 별도로 있으며 이 체크를 자동으로 채우지 않는다.

## 4. UT를 진행할 때 사용할 최소 안내 — 검토용 초안

이미 합의한 것: 정상·지연·시각 미확인 3상황, 상태 의미/기준 시점/입차 보장 여부 3요소 관찰, 개선안 이해도부터 확인. [UT_DESIGN.md](../ut/UT_DESIGN.md)를 따른다.

참여자 과업 예시:

> 테스트 상황은 오늘 낮 12시입니다. 이 화면은 연구용 모형이며 상품·현황은 가상값입니다. 성수동에서 이용할 주차장을 골라주세요. 선택을 마치면 알려주세요.

중립 후속 질문:

> 어떤 정보를 근거로 선택했나요?
> 이 화면으로 확실히 알 수 있는 것과 아직 알 수 없는 것은 무엇인가요?

진행자 관찰용 빈 양식:

| 기록용 구분 | 상황 | 선택/보류·이유 원문 | 상태 의미 | 기준 시점 | 입차 보장 여부 | 도움 수준·막힌 지점 |
| --- | --- | --- | --- | --- | --- | --- |
|  |  |  |  |  |  |  |

3요소는 ‘정확/오해/설명 없음’으로 기록하고, 자발 설명·중립 질문 후·힌트 후를 구분한다. 표의 구분은 이름 등 개인정보 대신 P01 같은 기록용 표시를 쓸 수 있다. 아직 모집 인원·시간 제한·성공률 기준을 정한 것은 아니다.

진행자 화면의 메뉴가 힌트가 되지 않게 사용자 1안 선택으로 참여자용 보기를 추가했다. 참여자용 보기는 진행자 메뉴·비교 모드·내부 상황 이름을 숨기며 상황별 링크로 시작한다. 이번 마감에 실제 UT 실시까지 새로 요구하는 것은 아니다.

- [ ] 팀이 과업·후속 질문·관찰 방법을 확인했다.
- [ ] 진행자 메뉴가 참여자의 답을 유도하지 않게 보여줄 방법을 정했다.

## 5. 선택 기록과 팀 검토 결과

A. 참여자에게 보여줄 화면 방식

1. 추천: 참여자용 보기를 추가해 진행자 메뉴를 숨긴다. 진행자는 미리 고른 3상황 링크로 진행한다. 현재 상태 전환 기능은 진행자 화면에 유지한다. 사용자가 1안을 선택해 구현·Chrome 검사를 마쳤다.
2. 코드 변경 없이 진행자가 조작하고 참여자가 선택/이유를 말하는 관찰형으로 진행한다. 조작 사용성까지 확인한 결과로 해석하지 않는다.
3. 현재 전체 화면으로 팀 리허설까지만 한다. 실제 사용자에게 보여줄 방식은 후속 UT 준비로 남긴다.
4. 기타: 사용자 직접 작성.

B. 팀 최종 검토 결과/다음 행동

1. 추천: 이 표의 설계 설명·3상황·과업/기록 방법을 함께 확인한 뒤 보완점만 알려준다. 답변 ‘1’만으로 확인 완료로 처리하지 않는다.
2. 설계 설명에서 막힌 부분을 먼저 보완한다. 위치/내용을 알려준다.
3. 팀이 위 항목을 이미 직접 확인했고 추가 보완이 없다고 명시한다. 그때만 팀 검토 완료로 기록한다.
4. 기타: 사용자 직접 작성.

기본 산출물 준비와 팀 최종 검토 결과를 구분한다. 이번 파일 생성이나 AI 판단으로 팀 검토·실제 UT·운영 구현 완료를 기록하지 않는다.

## 최신 검토 상태

사용자는 B3를 선택하면서 ‘유미·종현만 확인, 수연은 검토 예정’이라고 명시했다. 유미·종현의 기존 결과물 검토를 확인 완료로 기록한다. 이후 참여자용 보기 추가는 AI 구현·검사 완료이며 수연 검토에 포함한다. 수연 승인이나 참여자용 보기의 팀 재검토까지 완료로 추정하지 않는다.
